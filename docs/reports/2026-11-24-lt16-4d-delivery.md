## 一、本轮解决的问题

### 1. `remote` 频道从零到翻面（LT-16.4d）

五个新 crate/模块构成完整链路：

```
RemoteChannel（8 方法 + 1 事件）
  ├── RemoteSessionRegistry      连接复用、generation、取消语义、workspace 运行时归属
  ├── RemoteTransportRouter      按 target kind 分派（未注册 kind 报准确错误）
  │     └── LanTransportPort     ✅ 唯一的已落地传输
  ├── ScopedServerRegistry       attach/detach 的 scoped 服务面
  └── rpc-client                 ChannelClient + LAN WS 传输（Rust 侧此前完全没有客户端）
```

新版块共 **5 个 crate**（`rpc-client`、`remote-session-registry` 新建；`rpc-host`、
`workspace-identity`、`host-channels` 扩展），自动测试 **约 60 条**。

**为什么先做 RPC 客户端**：核代码时发现四种 transport 的卡点表面不同、根因相同——Rust
只有 `ChannelServer`（服务端），没有 `ChannelClient`。补上之后 LAN 只剩「换票 + 建连」，
SSH 只剩「拉起 stdio」，v3 只剩「套 Noise」。

### 2. `remote-desktop` 会话面的纯逻辑（LT-16.4b 续段）

- **会话状态机**（10 条测试）：准入顺序、同意等待、两个 TTL、被控态通知。
  两个 TTL 缺任一个都会把被控端**永久卡在 busy**。
- **显示器校验 + 编码能力**（6 条测试）：TS 的 7 条过滤 + 6 条归一；编码能力的
  从结果映射 / 读 / 写三步。

### 3. LT-14 的两个写死字段

| 字段 | 状态 |
| --- | --- |
| `hasBackgroundWork` | ✅ 接 `TaskRegistry::has_running()` |
| `workflowActivity` | 🟡 派生器已落（14 条测试），**数据源未接**（Rust 投影的 `workflow_runs` 仍是 `None`；产品路径由 TS 投影产出，用户侧无缺失） |

`hasBackgroundWork` 的关键取舍：`upsert` 拆成两条路径——store 路径**保留**已有布尔
（store 不知道 ≠ 确认没有），运行时路径显式给事实。

### 4. LT-8 TUI Enter

原来只做本地回显，用户按 Enter 看到「已提交」但没有任何 RPC。现在走 `session/send`，
并有在途/拒绝/回执对齐语义。**输入行只在受理后清空**（失败时保留用户的字）。

## 1. 结论与改造目标

0.0.92 安装版核心链路通过：启动、基础对话、帮助菜单导出日志、托盘隐藏/恢复、

### 3.1 为什么必须换会话

当前验收会话的进程链是
`node_repl(25744) → agent(18044) → Host(14364) → ModeTauri(9172)`。壳的
`HostSupervisor::kill_current` 与重生收摊都走 `taskkill /T`，会连带杀掉执行验收的
agent 与插件宿主，因此无法在同一个 turn 内既杀 Host 又观察结果。

执行者必须是以下任一形态，且**不能**是目标 Host 的后代：

- 独立的 PowerShell 进程（`Start-Process` 从 explorer/任务计划启动，父进程不是 Host）；
- 另一个 Mode CLI 会话（不挂在该 Desktop Host 下）；
- 第二台机器通过 SSH/WinRM 驱动本机。

### 3.2 编排步骤

1. **基线**：记录当前 Host pid、`startupId`、终端 shell pid 与父进程、终端心跳文件路径。
2. **用例 A（自然死亡）**：`taskkill /F /PID <host>`（**不加 `/T`**，模拟进程崩溃而不是
   壳主动收摊）；轮询进程表与 Host 日志，等待新 `startupId`；确认页面 reload、终端
   心跳文件继续增长、终端 shell 仍存活且父进程仍是 `ModeTauri.exe`。
3. **用例 B（半开管道）**：用 `NtSuspendProcess` 挂起 Host 全部线程；等待至少
   `2 × 30s ping 间隔 + 10s deadline`；确认渲染层连续两次无 pong 后发出 `kill`、
   Host 被换代、页面 reload；确认终端仍存活。
4. **用例 C（崩溃循环）**：60 秒内连续杀 Host 四次；确认第三次后暂停自动重生、
   失败屏出现且带「重试」；用 UIAutomation 点击「重试」（或人工点击），确认新 Host
   启动、页面回到可用态。
5. **证据落盘**：每一步写 JSON/Markdown 到
   `.plan/accept-0.0.92-destructive/`，包含时间、pid、startupId、进程树、终端心跳
   文件大小、失败屏文案与点击前后截图。脚本本身建议放
   `scripts/acceptance/host-kill-orchestrator.ps1`（提交前先确认是否需要入库；
   一次性脚本可留在 `.plan/`）。

### 3.3 判据

- 用例 A/B：新 `startupId` 与旧代不同；页面回到可用态；终端心跳文件在 Host 死亡
  时间点之后仍有新行；终端 shell 进程未重启。
- 用例 C：失败屏出现「重试」；点击后出现新一代 Host 并完成启动闸门；不要求保留
  崩溃前的任务状态（spec 只承诺重生与可见失败）。
- 任何一步失败都要保留 Host 日志尾部与进程快照，不在验收脚本里自动清理现场。

### 3.4 风险

- 用例 A 不加 `/T` 可能留下 Host 子进程孤儿；验收结束要按 pid 表清理并记录。
- 用例 B 挂起 Host 会让所有 RPC pending，必须确认 watchdog 的 kill 路径真的触发，
  而不是人工 resume 后误判通过。
- 用例 C 的失败屏可能被连续四次 kill 之外的旧预算影响；每轮开始前确认
  `HostSupervisor` 的退避预算已稳定运行 ≥60 秒。

## 4. P0-2 远程工作区任务通知

### 4.1 现象与证据

- 三次任务完成（含窗口隐藏、窗口失焦）均无 toast；全屏帧和 Windows 通知库都没有

### 4.2 假设与排查顺序

1. **H1：远程 attachment 下 sessions-index 不进入 `live`**（最可能）。
   在本地工作区重复同一任务，若本地出 toast 而远程不出，即锁定远程链路。
2. **H2：隐藏/失焦窗口的渲染层节流导致 hook 没观察到 phase 边沿**。

3. **H3：`showTaskNotification` 调用失败被 `fireAndForget` 吞掉**。
   在 `tauri-invoke-shim` 的 `fireAndForget` 失败分支加 `logger.warn`（生产构建目前
   `logger.warn` 可能 no-op，需要 Host 文件日志或 debug 通道承接），复现后看错误码。

### 4.3 修复选项

- **若 H1 成立**：先明确产品规则——远程工作区是否承诺桌面通知。
  - 承诺：通知不能只依赖远程 sessions-index；需要从会话快照的 phase 边沿产生通知，
    或在 Host 侧提供与工作区无关的任务终态事件。两条路都要先写 spec，避免出现
    「本地能通知、远程静默」的隐性差异。
  - 不承诺：在设置页/文档中明确远程工作区限制，并确保 UI 不暗示已开启通知。
- **若 H2 成立**：不要在隐藏窗口里依赖定时器；把通知意图下沉到不随窗口可见性暂停的
  通道（Host 事件或壳通知命令），或在窗口重新可见时补发并去重。
- **若 H3 成立**：修正错误处理并让失败可见；通知失败不能静默。

### 4.4 验收

- 本地工作区：窗口隐藏/失焦时任务完成 → 2 秒内出现 toast，标题/正文正确。

## 5. P1-1 出站远程桌面首帧

### 5.1 现象

本机作为主控连接 MX121212（`100.68.49.120:45880`）时，界面进入
「已连接，等待对端首帧…」，`0 fps / 0.0 Mbps`；本机 Host 日志只有
`controller session requested` 与 `controller signal socket connected`。本机被控
方向的 Helper 已独立验证可用，所以不能把问题归到本机 Helper。

**日志归属更正（2026-10-29 复核）**：本节原先用「主控日志里没有 `media start
requested`」当失败证据，这是错的。该行只由**被控侧**打印
（`remoteDesktopControlledCoordinator.ts:167`），主控侧无论成败都不会出现它；主控侧
主控会话的日志只有 `controller session requested` 与 `controller signal socket
connected`（`remoteDesktopController.ts:153/294`）。按会话键分区复核
`host-2026-10-27.log`：两处 `media start requested, displayId=0`（209、267 行）都属
被控块 `clientId=5689c163-4ac4-406c-8b4a-c89111ad2174`，且这些块一路走到
`media ws ready received`；主控块 `serverId=f487505c-8510-4d8f-8b92-112d4fabafb2`
（135–136 行）只有上面两行。也就是说：**本机被控媒体面是通的，主控方向缺的是对端
出流**，不能从本机日志推出「主控没建媒体面」。

### 5.2 诊断步骤

1. 确认对端 Mode 在前台、已同意远程桌面、未被最小化到托盘；必要时让对端操作者
   复述同意窗状态。
2. 取对端 Host 日志，检查是否有 `consent requested`、`media start requested`、
   `rd_media_start failed`；区分「未收到请求」「Helper 不可达」「编码器不可用」。
3. 在本机主控日志里补一条关联 id（controller session id）并确保 `media start`
   请求与响应可对应。注意口径：`lan-remote-desktop-native-media.md`「媒体面可观测性与
   首帧约束」只要求零帧区间 **warn + 页面切「等待对端首帧…」**，不要求把它判成终态
   （`firstFrameWatchdog.ts` 的 `onNoFrames` 只落日志与 UI 态）；要验终态的是「连不上
   对端」，那条走 `remoteDesktopController.start()` 的失败分支
   （`peer session request failed (serverId=…)` + `session phase=closed`）。
4. 若对端 Helper 正常但仍无首帧，检查 LAN/relay 媒体 socket、NAT/防火墙与
   `rd-media-relay` 的 helper pipe 连接。

### 5.3 验收

- LAN 与 relay 两条路径各一次：首帧在 5 秒内出现，fps/码率恢复。
- 对端不可用时：会话在既有超时内进入「对端不可用/连接失败」终态，不长期停在
  「等待对端首帧」。
- 被控侧日志能从 `consent allowed` 追到 `media start requested` 或明确的失败原因。

### 5.4 复核结论（2026-10-29）

1. **对端恢复在线**：`Resolve-DnsName MX121212` → `mx121212.tail315cc8.ts.net.`

   → `TcpTestSucceeded=True`。原先记的「对端离线」不再成立，依赖口径改为「对端需有人
   值守」（见下条）。
2. **主控侧失败分支已按代码确认**：`remoteDesktopController.start()` 在

## 9. P2-3 终端跨 Host 死亡真机验收

依赖 P0-1 的编排脚本。在用例 A/B 中同时断言：

- 终端 shell 与 conhost 进程 pid 不变，父进程仍是 `ModeTauri.exe`；
- 终端心跳文件在 Host 死亡时间之后继续增长；
- 页面 reload 后终端面板重新订阅，历史输出与当前输入可用；
- Host 换代后新终端仍走壳侧 PTY，不回落 Host 的 node-pty 路径。

### 9.1 P2-4 终端跨整页 reload 的持久化/reattach（2026-10-27 新登记）

**证据**：P0-1 Case A 前终端 `powershell.exe` 15652/26136 的父进程是
`ModeTauri.exe`（PTY 下沉本身成立）；Host 14364 被 `taskkill /F`（不加 `/T`）后
壳换代到 25368，但整页 reload 后 `terminalShellsAfter=` 为空。spec
`terminal-pty-in-shell.md` §3 规则 3 承诺「Host 崩溃/重生不碰终端」，当前实现只对
「Host 进程直接死亡」成立，对「Host 死亡 → 壳 reload 主窗口」不成立。

**根因假设**：terminalId 只存在于渲染层内存（bottom terminal 的
`terminalIdRef` / side pane 的模块级 registry），整页 reload 会销毁 JS 上下文；
壳侧 `TerminalSessionManager` 仍持有 PTY，但渲染层没有 `list/attach` 接口重新挂接。
bottom terminal 在 unmount 时还会 `terminalService.dispose`，进一步杀掉 PTY。

**设计选项**：

1. **壳侧会话注册表 + reattach（推荐）**：壳增加 `terminalList` / `terminalAttach`
   / `terminalReplay` 命令；渲染层把 terminalId 按 workspace 持久化到
   `sessionStorage`，reload 后先 list/attach，再订阅事件。壳为每个终端保留有界
   输出环（例如最近 256 KB）供 replay；不承诺完整历史，但当前屏幕可用。
2. **只阻止 bottom terminal 在 reload 前 dispose**：不解决 terminalId 丢失，
   reload 后仍无法重新挂接，只减少「主动杀 PTY」；不单独采用。
3. **Host 死亡不 reload 整页**：与 §22.4 的 reload 语义冲突，不采用。

**验收**：

- 打开终端跑持续心跳 → 杀 Host → 页面 reload 后终端标签重新出现并 attach 到同一
  PTY；shell pid 不变、心跳文件继续增长。
- 仅 Ctrl+R 手动 reload 同样能 reattach。
- 关闭终端标签才 dispose PTY；应用退出杀全部 PTY；reload 不留孤儿 PTY。
- 若选择不保留 scrollback，UI 明确提示「历史输出已丢失，进程仍在运行」，不伪装成
  完整恢复。

**spec 落点**：`docs/specs/terminal-pty-in-shell.md` §2 所有者表与 §3 规则 3，
补「文档级 reload 后的 reattach 事件序」。

## 10. 事件顺序与所有权

```
外部编排器（不属于 Host 进程树）
  ├─ 用例 A: kill Host ──> 壳 Supervisor 观察进程退出
  │                         ├─ 重生新代（0/2/10s 退避）
  │                         └─ reload 主窗口
  │                               └─ 新文档采用新 startupId → 启动闸门
  ├─ 用例 B: suspend Host ──> 渲染层 watchdog 两次无 pong
  │                         ├─ 发 kill 控制消息 → 壳杀当前代
  │                         └─ failCloseHostTransport + 终态屏
  └─ 用例 C: 4 次快速 kill ──> 退避预算耗尽 → 失败屏
                                  └─ 点击重试 → force_restart → 新代 + reload
```

所有者不变：Host 进程事实归壳 `HostSupervisor`；通知意图归渲染层 hook（若改远程
通知，需先明确是否下沉到 Host）；终端进程归壳 `terminal.rs`；导出过滤归壳
`exportLogs` 命令。

## 11. 非目标

- 不重写 Host 生命周期，不把 `taskkill /T` 改成按 pid 单杀来规避验收限制。
- 不为通知/首帧问题先加超时兜底；先定位再决定终态语义。
- 不在本计划内处理多窗口、插件市场、IM bot、Tauri 签名等既有独立项。
- 不在本计划内删除旧 Electron 日志文件；只决定导出时的过滤口径。

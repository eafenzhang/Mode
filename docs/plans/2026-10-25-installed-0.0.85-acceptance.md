## 观察项（2026-10-25 已排查；结论见各条）

1. **被控横幅残留 / 「结束」无效**（已定位到挂起层面）：横幅是 `RemoteDesktopIndicator`（renderer 覆盖层），渲染条件 = Host 推送的 `controlled` 状态；「结束」调 `platform.rdSetServerEnabled(false)` 走窗口 Host 的 rd 服务。会话结束后该按钮呈**禁用态**——对照源码 `disabled={busy}`，说明该调用**永久挂起**（`setBusy(true)` 后 `finally` 永不执行），不是点击未生效。
2. **设备卡片消失**（同源）：会话结束后设备列表 3→1；设备列表同样来自窗口 Host 的 LAN/RD 服务读路径。
3. **移动端弹层 LAN 地址不加载**（同源）：`WebRemoteControlDialog` 打开时调 `platform.getLanAccessState()`（`desktopPlatform` 先解析 `resolveLanAccessService()`，走窗口 Host RPC）挂起 → `lanLoading` 永真 → 停在「正在读取监听地址…」。
   **三者的统一机制（已确认挂起现象，挂起环节待复现）**：远程桌面会话异常结束后，该窗口的 Local Host 服务面进入不响应状态——除上述两处外，同一会话视图的模型选择器也常驻「正在加载模型…」（`modelSelectionService.getView` 同样走 Host）。RD 会话与任务/LAN 共用同一个 window-scoped Local Host，会话失败把整窗服务面拖挂，与 AGENTS.md「每窗口一个 Local Host」的架构一致。**挂起的具体环节（推测在 RD 会话异常结束的 Host 清理路径）需要 dev 版复现 + 服务日志**——安装版 0.0.85 不落盘任何文件日志（见第 4 条），真机无法取证。
   **恢复手段**：重启应用（单实例守卫下需先退出运行中的实例）。**修复方向**：找出 RD 会话清理路径的挂起点本身；按仓库纪律不先加超时兜底。
   **2026-10-25 重启复验（假设已验证）**：用户重启应用后逐项复查——被控横幅消失、设备列表恢复（MX121212 可用·局域网、EAFEN 可用·公网、EAFEN MCP）、移动端弹层左栏正常出二维码与 `http://<Tailscale 地址>:45880/` 且状态「等待手机连接 · 已就绪」。三个观察项全部确认为**运行态挂起症状**（无持久化损伤），「RD 会话异常结束拖挂窗口 Host 服务面」成立；剩余工作 = 定位 RD 会话清理路径的挂起点（需 dev 版复现 + 服务日志）。
   **修复已落地（同日，`d5ba0671`）**：挂起不在服务层（Host 写路径与 `requestState` 均自带超时），而在渲染层共享通道的死亡不可见——壳与注入桥如实发布 `phase:"failed"`，但 `main.tsx` 启动完成后把状态流静默丢弃，`ChannelClient` 永不 dispose。修复：post-boot failed → base 连接与全部 scoped session fail-closed dispose（挂起与后续 RPC 立即拒绝）+ 切既有启动失败终态。口径与开放项（`DatabaseStartupControl` 在 Tauri 无消费者、半开管道无心跳检测、Host 自动重生）见 `docs/specs/tauri-renderer-host.md` §22；门禁：typecheck / lint 0 error / architecture 0 / desktop 197（+6 新用例）/ ui 507 全绿。
4. **安装版不落盘日志**（新增发现）：`~/.mode/v2/logs/` 最新文件停在 2026-10-20，`%LOCALAPPDATA%/Mode`（安装目录）与 `%APPDATA%` 均无今日 Mode 日志——0.0.85 安装版的壳/sidecar/agent 均无文件日志输出。真机排障只能靠 UI 观察，这也是 LR-5 §27「`exportLogs` 产品设计」欠账的实证。
5. **fmt:check 本机全量失败**：见门禁表。属检出条件（autocrlf）与格式化器的换行符口径冲突，需要裁决收口方式，不在本机跑 fix。
6. **cargo 本机两处测试目标无法运行（根因链已推进一层）**：`mode-tauri` 的 `/MANIFEST` 链接参数在 gnu 下硬失败（已由 CI 纳入 `-p mode-tauri` 收口权威路径，`cb59bb52`）；`updater --lib` 的 `0xc0000139` 此前假设是 windres 缺失——**实验已推翻**（llvm-mingw 在 PATH 上、`tauri-test-manifest` 的 gnu 分支产出了 `.rc`/`.coff.o` 工件，但最终测试 exe 没有 `.rsrc` 节）：资源对象生成并声明为测试链接参数后，在 gnu 链接环节丢失（首要假设：rustc 对 gnu 目标默认的 `--gc-sections` 把无引用的资源节回收）。精确丢点待验（`llvm-objdump -h` / 试 `--no-gc-sections`）。CI/MSVC 仍是权威口径。

## updater 0xC0000139 收口（2026-10-26 凌晨）

本机 `cargo test -p updater --lib` 的测试二进制 `STATUS_ENTRYPOINT_NOT_FOUND (0xC0000139)`
悬案（曾登记为 gc-sections 回收资源节的待验假设）**根因查明并修复**。

### 证据链（全部实验复现）

1. **精确入口点定位**：写脚本把测试 exe 导入表 453 个符号与本机 33 个 DLL 实际导出全量
   比对（api-ms-* 映射到真实载体），唯一缺失：**`comctl32.dll` 的 `TaskDialogIndirect`**。
   该 API 只在 comctl32 **v6**（side-by-side）导出；绑定 v6 需可执行文件内嵌声明
   `Microsoft.Windows.Common-Controls` 6.0.0.0 的应用清单。对照：正式 `ModeTauri.exe`
   同样导入 TaskDialogIndirect 但**有 .rsrc 节**（manifest 在）→ 运行正常。
2. **gc-sections 假设被推翻**：`-v` 落盘完整 rustc 命令行，1364 字符里**没有任何

## Host 自动重生（2026-10-26，spec §22.4）

**设计**（所有权与事件序见 spec §22.4）：壳 `HostSupervisor` 持有可换代句柄；监督线程等
**进程事实**（`wait_for_exit`，reaper/主动收摊都唤醒）→ 退避策略（60s 内死亡记快速崩溃，
等 0/2/10s，3 次后暂停）→ 起新代 → **整页 reload**。注入桥不再写死 startupId，改为文档启动
时经 `host_startup_id` 采用当前代——这是 reload 能绑定新代的前提，也顺带移除了「外部字符串
拼进注入脚本」的旧注入面。终态屏 `database-startup-control` 由桥转发 `host_startup_control`
（retry/exit/snapshot），旧 Electron main 的消费者就此补齐。

**真机 E2E**（`HostRoundtripHarness`，产品接线，不碰已安装实例）：
1. 起 Host（pid 18484，`host-14960-...147481`）→ ready；
2. `taskkill /F` 杀 18484 → 立即重生 `host-14960-...175841`（pid 21220）→ ready；
3. 再杀 21220 → **2s 后**重生 `host-14960-...194270`（pid 18984）→ ready（退避节奏实测吻合）；
4. 看门狗退出 → `host_shutdown pid=18984`（收的是**当前代**）→ exit 0。

**验证面**：退避策略纯函数 4 用例、`wait_for_exit` 生命周期用例（进程退出与 shutdown 两条唤醒）、
桥的运行时采用/控制转发由 `windowModeInjection`（41 绿）与 `host-standalone` 对拍（3 绿）
覆盖；壳侧编译 + 三 harness 特性 clippy `-D warnings` 通过。

**边界**：多窗口不在口径（当前只有主窗口）；半开管道（进程活着但传输停摆）仍需独立心跳任务；

## 远程桌面「连不上」排查（2026-10-26，含一次结论更正）

用户报 MX121212 远程桌面连接失败。最终根因：**被控端（本机）的 CUA Helper 从未被创建**。

证据链：
1. 本机 Host 日志（被控方向）：`consent allowed` → `media start requested, displayId=0` →
   **`warn rd_media_start failed: Computer Use Helper is not reachable for rd_media`** →
   `rd_media_stop failed` → `media socket without session owner rejected`。
   媒体面拿不到 Helper，主控侧只能看到黑屏/「连不上」。
2. 安装包内 Helper 三件套在位且 sha256 与 runtime-manifest 完全一致（不是发运缺失）。
3. 装配层：`createLocalServices` 的 CUA Helper 准入
   （`shouldCreateDefaultCuaProductHelper`）要求 **`serviceAuthorityMode === "desktop-local"`
   严格相等**；旧 Electron main 装配过，**Tauri Host 移植时漏传**
   （`serviceAccessor.ts` 的 options 里没有这个键）→ 准入恒 false → Helper 永不创建，
   `rd_media_*`/raw_input 全部 fail-closed。

**更正**：排查中途曾据 `/api/server-info` 的 `version:"0.0.0-dev"` 与 `protocolVersion:1`
判断「对端协议过旧」，这是**误读**——`protocolVersion` 是 LAN API 版本
（`SERVER_REMOTE_PROTOCOL_VERSION` 恒为 1），`version` 是构建注入的 `MODE_VERSION`
（未注入时回落 `0.0.0-dev`），两者都不反映远程桌面信令版本。用户确认两端均为 0.0.87，
该结论作废。

修复：
- `serviceAccessor.ts` 传入 `serviceAuthorityMode: "desktop-local"`（含注释说明为何不能删）；
  新增装配守卫 `host-cua-authority-wiring.test.mts`（静态断言该键存在）。
- 保留同期加入的**握手超时**（`9b5b8827`，15s/不可重试）作为静默对端的兜底——与本根因
  无关，但同样是「永久挂着」的必要出口。
- 设置页现有事实（截图）：4 台已配对设备「远程桌面：已授权（连接免确认）」、本机无可用
  硬件编码器（回退系统软件编码）、「本机正在被远程控制」横幅——均属预期。

验证：审批准入单测（services 464 通过）、装配守卫、desktop 225 通过、typecheck/lint/架构全绿。

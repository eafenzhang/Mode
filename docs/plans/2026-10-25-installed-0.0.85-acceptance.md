## 观察项（2026-10-25 已排查；结论见各条）

1. **被控横幅残留 / 「结束」无效**（已定位到挂起层面）：横幅是 `RemoteDesktopIndicator`（renderer 覆盖层），渲染条件 = Host 推送的 `controlled` 状态；「结束」调 `platform.rdSetServerEnabled(false)` 走窗口 Host 的 rd 服务。会话结束后该按钮呈**禁用态**——对照源码 `disabled={busy}`，说明该调用**永久挂起**（`setBusy(true)` 后 `finally` 永不执行），不是点击未生效。
2. **设备卡片消失**（同源）：会话结束后设备列表 3→1；设备列表同样来自窗口 Host 的 LAN/RD 服务读路径。
3. **移动端弹层 LAN 地址不加载**（同源）：`WebRemoteControlDialog` 打开时调 `platform.getLanAccessState()`（`desktopPlatform` 先解析 `resolveLanAccessService()`，走窗口 Host RPC）挂起 → `lanLoading` 永真 → 停在「正在读取监听地址…」。
   **三者的统一机制（已确认挂起现象，挂起环节待复现）**：远程桌面会话异常结束后，该窗口的 Local Host 服务面进入不响应状态——除上述两处外，同一会话视图的模型选择器也常驻「正在加载模型…」（`modelSelectionService.getView` 同样走 Host）。RD 会话与任务/LAN 共用同一个 window-scoped Local Host，会话失败把整窗服务面拖挂，与 AGENTS.md「每窗口一个 Local Host」的架构一致。**挂起的具体环节（推测在 RD 会话异常结束的 Host 清理路径）需要 dev 版复现 + 服务日志**——安装版 0.0.85 不落盘任何文件日志（见第 4 条），真机无法取证。
   **恢复手段**：重启应用（单实例守卫下需先退出运行中的实例）。**修复方向**：找出 RD 会话清理路径的挂起点本身；按仓库纪律不先加超时兜底。
4. **安装版不落盘日志**（新增发现）：`~/.mode/v2/logs/` 最新文件停在 2026-10-20，`%LOCALAPPDATA%/Mode`（安装目录）与 `%APPDATA%` 均无今日 Mode 日志——0.0.85 安装版的壳/sidecar/agent 均无文件日志输出。真机排障只能靠 UI 观察，这也是 LR-5 §27「`exportLogs` 产品设计」欠账的实证。
5. **fmt:check 本机全量失败**：见门禁表。属检出条件（autocrlf）与格式化器的换行符口径冲突，需要裁决收口方式，不在本机跑 fix。
6. **cargo 本机两处测试目标无法运行（根因链已推进一层）**：`mode-tauri` 的 `/MANIFEST` 链接参数在 gnu 下硬失败（已由 CI 纳入 `-p mode-tauri` 收口权威路径，`cb59bb52`）；`updater --lib` 的 `0xc0000139` 此前假设是 windres 缺失——**实验已推翻**（llvm-mingw 在 PATH 上、`tauri-test-manifest` 的 gnu 分支产出了 `.rc`/`.coff.o` 工件，但最终测试 exe 没有 `.rsrc` 节）：资源对象生成并声明为测试链接参数后，在 gnu 链接环节丢失（首要假设：rustc 对 gnu 目标默认的 `--gc-sections` 把无引用的资源节回收）。精确丢点待验（`llvm-objdump -h` / 试 `--no-gc-sections`）。CI/MSVC 仍是权威口径。

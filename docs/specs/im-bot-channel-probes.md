## 为什么单开一份清单

下面的能力**都取决于平台侧行为，而我们的代码里没有任何证据**。在没有结论前写实现，
等于按猜测加分支——正是 `AGENTS.md` 里"不不断增加兜底分支"要避免的事。
每项都给出：问题 → 为什么阻塞 → 怎么探 → 两种结论各自的分支。

主力通道是**企微与微信**，因此按它们排序。

## P1 微信单条文本上限（阻塞：长回复的可靠性）

- **问题**：`splitLongReplyText` 用 3500 字符做全局硬上限，这个数是**假设**，没有微信侧依据。
- **为什么阻塞**：若微信上限更小，超限消息会被服务端拒绝 → 走停放补投（`bot-outbound-delivery.md`）
  → 用户端表现为"这个问题没回复"，而且重试也会同样失败。
- **探针**：给微信 bot 发一条 4000+ 字符的回复（例如让它输出长列表），看 `sendmessage` 的返回码
  与用户端是否收到；再二分出实际阈值。
- **分支**：阈值 ≥ 3500 → 维持现状；更小 → `splitLongReplyText` 的限额按 provider 分档
  （微信取实测值的 80%），并补一条 provider 契约测试。

## P2 微信能否编辑已发消息（阻塞：微信要不要做打字机）

- **问题**：iLink 的 `message_state=1`（流式/中间态）服务端是否接受、客户端是否原地刷新。
- **为什么阻塞**：这决定微信**能否从"逐块气泡"升级为"单条消息原地增长"**。现在微信不支持
  `streaming_card`，`assistant_changes` 的逐块刷出（`49f59ced`）就是它的上限。
- **探针**：同一 `client_id` 连续发 `message_state=1` 的多帧，最后一帧 `message_state=2`，
  观察客户端是否只显示一条并在原地增长。
- **分支**：可编辑 → 给微信加 `streaming_card` 能力（`getSupportedBotReplyGranularities`）；
  不可编辑 → 现状即终态，把这条结论写进 `bot-reply-granularity.md` 的 provider 矩阵注释。

## P3 引用原消息（阻塞：G3）

- **问题**：企微 `replyStream` 能否携带被引用消息 id；微信 `item_list` 有没有引用类型。
- **为什么阻塞**：G3 的达标定义是"平台支持时引用触发消息"，不支持时走既定降级
  （不换收件人）。不探明就不知道哪条通道该走哪支。
- **数据侧已就绪**：`BotActor.providerMessageId` 已解析（企微 `body.msgid`、微信 `readWeixinMessageId`），
  缺的只是出站携带。
- **分支**：支持 → 出站带引用字段（按 provider 各自实现，服务层不分支）；不支持 → 记录为
  与参照产品的既定差异，不做假界面（`R4 平台能力分档，不造假界面`）。

## P4 群成员名目录（阻塞：G4）

- **问题**：能否按 userId 查到群成员昵称。
- **已有线索**：`messages.ts` 的群聊启用说明里已经在引导用户开通
  `im:chat.members:read`（"查看群成员，用于显示发送者用户名"）——说明**企微侧有该能力**；
  微信 iLink 在 `providers/weixinProvider.ts` 里**没有任何成员目录接口**。
- **分支**：企微 → 实现进程内成员名缓存 + 失效策略（可丢，权威在平台），并把它接进
  群提示词的 `[from: 名字]` 与历史渲染（现在的兜底文案是"未知成员"）；
  微信 → 维持兜底文案，写进 spec 的既定差异。

## P5 群历史落盘的真机确认（阻塞：无，属验收）

- G7 的落盘已实现（`aea3714c`），但"重启后历史仍在"要真机确认：
  企微群里连续说三件事（都不 @）→ @ 一次让它总结（三件事都在上下文里）→ 重启 Mode →
  再 @ 一次（历史仍在）。对应 `im-bot-group-chat-alignment.md`「G7 实现口径」的验收 4。

## P6 需人工介入的错误信号（阻塞：G8）

G8 要区分"可恢复"与"需人工介入"，就必须有平台侧的具体信号（错误码 / 事件帧）。
已确认的线索：**钉钉 Stream 运行时订阅了 `{ type: "EVENT", topic: "*" }`，但 provider 只处理
message topic，其余事件帧被直接忽略**——"机器人被移出群"若有事件，就在那批帧里。

- **P6a**：钉钉把 EVENT 类帧原样打点（加一次 debug 日志即可，不改行为），确认是否有
  "机器人被移出群 / 权限变更"类事件；
- **P6b**：企微、飞书是否有群成员变更事件；
- **P6c**：收集各平台"权限不足"的真实错误码（触发方式：不给群成员读取权限时调对应接口）。
- **分支**：有信号 → 在投递失败分类里加"需人工介入"级，走既有一次性提示位
  （`bot-outbound-delivery.md` 的 `deliveryNoticeAt`），文案写明"需要管理员做什么"；
  无信号 → 维持现状并把"静默失败"写成 spec 里的既定差异（不造假界面）。

## P7 钉钉的等待期反馈是否可做（阻塞：钉钉用户的"无反馈"）

- **现状**：钉钉与 webhook 没有任何等待期反馈（`im-typing-feedback.md` 明列为另立任务）。
  钉钉有 AI 卡片能力（`dingtalkUseAiCard` + 模板 ID），理论上可以照企微的做法开一条静态占位卡
  并在出站时同流接管。
- **但受配置门控**：`supportsStreamingCardReply` 在未配置 AI 卡片时直接返回 false（回退 Markdown 摘要），
  所以占位卡只对"已开启 AI 卡片"的钉钉用户成立——收益面比企微窄。
- **探针**：开启 AI 卡片后，turn 起跑时用 `createStreamingReplyCard` 建一条只有"正在处理"的卡片，
  出站时用同一 `providerUserId`/streamId 接管，确认客户端是否原地更新且不残留。
- **分支**：成立 → 实现（沿用企微占位流的键与接管语义，不要再造一套）；不成立 → 维持"钉钉无反馈"，
  写进 `im-typing-feedback.md` 的既定差异。



维持现状（不实现），理由与耦合关系见
[im-bot-group-chat-alignment.md](./im-bot-group-chat-alignment.md)「G10 复核与处置」：

- 成环前提由 G5 打开——回复一旦产生平台级 @ 实体，企微/钉钉的 @ 门控与飞书的 mention 判定
  就都会让对方的回复变成触发源，因此**G5 与 G10 必须同批决策**；
- 而 G5 在主力通道上收益最低：微信没有 @ 语法，企微只在被 @ 时才收到群消息（回复者本来就在
  和机器人对话，@ 回人的信息量很小）。

若要恢复 G5（例如飞书成为主力），先做 P3/P4 的探针，并在同一批里实现互答保护。

## 探针的落地方式

每项探针都应留下**可复现的证据**（命令 + 原始响应 + 时间），结论写回对应 spec 的
"待实机"条目并改为已确认；不要只把结论留在对话里。

## 背景

用户指令（2026-10-14）：「按完整功能对齐」，指群聊对话能力。诊断结论：当前群聊是**精简自研版**
（内存历史缓冲 + 提示词注入 + 澄清/静默），而仓库里存在一整套群聊能力模块，**10 个全部未被
`botsService` 引用**：

`topicHistory`、`channelReply`、`channelMentionResolver`、`groupQueueCard`、`groupSessions`、
`groupDeliveryThrottle`、`groupResultDelivery`、`groupAdminAttention`、`topicContinuation`、
`groupMemberDirectory`。

### 为什么不能"直接接上"

两条独立的原因：

**1. 它们是上游衍生实现，clean-room 纪律禁止读。**
按 `docs/specs/clean-room-policy.md` 认可的口径（对 `upstream/zcode-baseline` 逐文件比对），
上述 10 个模块里 **9 个与基线逐字节相同**（`topicHistory`、`channelReply`、
`channelMentionResolver`、`groupQueueCard`、`groupSessions`、`groupDeliveryThrottle`、
`groupResultDelivery`、`groupAdminAttention`、`topicContinuation`），只有 `groupMemberDirectory`
是基线中不存在的自有文件。政策原文：「不读取本仓库中上游衍生的实现文件作为编写参考」、
「翻译、对照改写、'按上游思路复现'均属读实现，一律禁止」。

**2. 它们依赖的领域模型与我们结构不同，不是改 import 能补的。**
例：`groupSessions` 用 `actor.threadId`、`actor.conversationThreadId`、`context.group`；
而我们的 `getBotActorConversation`（`packages/shared/src/bots.ts:379-393`）只接受
`chatType | providerUserId | chatId`，**群会话按 chat 作用域，没有话题/线程维度**。
`channelReply` 依赖的 `ChannelReplyHostRequest`、`BotGroupDelivery` 等类型在我们的
`@mode/shared` 里也不存在。

结论：**"接上现成模块"不可行**（既违纪律、也缺模型）。本 spec 走 clean-room 重实现。

### 本 spec 允许的输入（与政策一致）

- **接口面**：上述模块的导出签名与类型声明（导出函数名、参数与返回类型）——已用于下面的能力清单；
- **测试断言**：`packages/services/test/` 下群相关测试的输入输出（不含实现体）；
- **黑盒对拍**：在基线检出上运行旧实现，观察输入输出与事件序列；
- **行为分析**：团队已完成的 `MyAgents-分析报告.md`（§5）；
- **本仓库 spec 与 DESIGN.md**。

**不允许**：打开上述 9 个模块的实现体照抄或翻译；不得把它们作为"按上游思路复现"的依据。

### G7 实现口径（2026-10-16，已落地）

**要解决的问题**：群历史此前是纯内存缓冲，重启即丢；`drain()` 取走即清空，被触发一次之后
"刚说过的事"就没了。这两点让机器人反复失忆。

**设计取舍（本项唯一有争议的地方）**：历史**不放进 `bot-state`**。
原因是写放大——群消息高频入站，而 `bot-state` 的每次写入都是**锁内全量 RMW + 全文件重写**，
且该文件多窗口共享。把历史挂进去，等于让每条未被 @ 的群消息都触发一次全量状态写盘。

因此：

1. **独立文件** `bot-group-history.v1.json`（`getAppConfigDir()` 下，经
   `withFileLock` + `atomicWritePrivateTextFile`，与 `bot-state`/`bot-bindings` 同一套私有写盘纪律）；
2. **进程内缓冲 + 去抖落盘**（2s）：append 只改内存并把整份快照排队，定时器 `unref()`，
   不阻塞进程退出；终态/退出时补一次同步 flush；
3. **可丢性显式声明**：历史只是"机器人未参与期间的参考上下文"，崩溃最多丢最近 2s 的追加。
   这条是本 spec 明确接受的取舍，**不允许**用"不可丢"的措辞回头把它塞进 `bot-state`；
4. **上限与截断保持**（单群 30 条 / 单条 200 字符 / 最多 200 群，LRU 淘汰）；
5. **读取语义改为快照**：`drain()`（取走即清空）→ `snapshot()`（读取不清空），
   被触发后历史仍在，同一群下次触发仍能看到之前的内容。

**状态所有者**：新增一个所有者（群历史文件），但**不与 `bot-state` 共享写入路径**——
它不经过 `BotsRepo.mutateState`，也不参与配置/运行态的任何一致性约束。

**验收场景**

1. 单测（`bot-group-history.test.ts`）：
   - `snapshot()` 读取后历史仍在（对比旧 `drain()` 语义的回归点）；
   - 单群 30 条上限、单条 200 字符截断、200 群 LRU 淘汰；
   - `hydrate()` 幂等、非法快照被忽略、`clearBot` 只清该 bot；
   - 持久化模块：load 缺失文件返回空、写盘走原子写、去抖多次 append 只落盘一次；
2. 源码契约：触发回合的读取走 `snapshot`（源码中不再出现对群历史的 `drain` 调用），
   且 append/clear 之后有落盘排队。
3. 回归：`pnpm --filter @mode/services test`、`pnpm typecheck`、`pnpm lint`、
   `pnpm architecture:check --changed` 全绿。
4. **待实机**：企微群里连续说三件事（都不 @），@ 一次让机器人总结——三件事都应在上下文里；
   重启 Mode 后再 @ 一次，历史仍在。

### G10 复核与处置（2026-10-16）

**结论：暂不实现，但把它与 G5 绑定。** 逐通道核实"机器人互答成环"的**前提**后，四条通道上都不成立。
（本节的结论**替代**上方能力清单 G10 行的「现状」列，并**作废**状态所有者表中
「去重/互答计数（G10）」那一行。）

| 通道 | 成环前提是否成立 | 证据 |
| --- | --- | --- |
| 微信 weixin | **不成立**（结构性阻断） | 入站解析直接丢弃机器人消息：`message_type === 2` 即 `return null`（`providers/weixinProvider.ts:611`，常量 `WEIXIN_MESSAGE_TYPE_BOT`）。我们的出站也以该类型发送，故双方都不会把对方的回复当用户消息。 |
| 企微 wecom | **不成立** | 平台**只在被 @ 时**下发群消息（`resolveBotGroupChatCapabilities("wecom").always === false`）；而我们的回复是纯文本、从不产生平台级 @ 实体。 |
| 钉钉 dingtalk | **不成立** | 群聊回调由 `isInAtList` 门控（`providers/dingtalkProvider.ts:137`），同样只在被 @ 时到达。 |
| 飞书 feishu | 理论上成立，实际未发生 | 飞书群回调**不**做 @ 门控（`always: true`），且我们确实没校验 `sender.sender_type`——但触发仍要求对方以**真实 mention 实体** @ 我们，而我们的回复从不产生 mention，所以链无法自持。 |

**因此不新增"互答计数 + 消息去重"这套机制**：在没有真实触发路径时加它，属于 AGENTS.md 明令避免的
"不断增加兜底分支"，还会引入一个可丢的进程内状态（上表状态所有者里那行也随之作废）。

**耦合注意点（本项真正的产出）**：成环前提由 **G5「按名字 @ 回人」** 打开——
一旦回复开始产生平台级 @ 实体，企微/钉钉的 @ 门控与飞书的 mention 判定就都会让对方的回复变成触发源。
所以：**G5 与 G10 必须同批决策**——做 G5 时同时实现互答保护（条数上限 + 去重），否则两项都不做。
当前建议是两项都不做（微信无 @ 语法、企微只在被 @ 时收消息，G5 在主力通道上收益本就最低）。

## 关键决策（需用户拍板）

**D1 会话作用域是否升到话题级？** —— **已结案：不升（用户 2026-10-16 决定）。**

判定依据（同期核实的平台事实）：本仓库四个产品通道里**只有飞书有话题维度**——
`providers/` 的入站解析至今没有读取任何 `thread_id` / `root_id` / `parent_id`，
而企微（只在被 @ 时下发群消息）、微信（iLink）与钉钉（`conversationType` 只有单聊/群聊）
**平台侧没有话题概念**。主力通道是**企微与微信**，升维的成本（`BotActor` 协议面 +
每条 provider 解析 + 会话键 + 状态文件迁移 + 桌面会话映射）落在四条通道上，
收益却只可能出现在飞书——成本收益不成比例。

后果（三项能力的处置）：

- **G6 话题隔离**：移出范围。群会话键维持 `group:<chatId>`，不引入线程维度；
- **G9 话题输入合并**：降级为"同群时间窗合并"，不再声称按话题分区；
- **G7 群历史持久化**：**保留，且不依赖 D1**——它要解决的是内存缓冲、重启即丢、
  单群 30 条 / 单条 200 字 / `drain()` 取走即清空，落进 `bot-state` 即可，不需要话题分区。
- 其余 G1–G5、G8、G10 均不依赖话题维度，维持原判。

若日后飞书话题群成为真实高频场景，再单独评估 D1（键可设计为 `[botId, chatId, threadId?]`，
无话题通道自动退化，避免一次性状态重写）。

### 原始问题记录（2026-10-14，保留以备追溯）

G6 / G7 / G9 都依赖"话题"这个维度，而它是**我们领域模型里目前不存在的概念**。引入它意味着：

- `BotActor` 增加 `threadId`（平台话题/线程 id）并在群分支参与会话键；
- `BotContextState` 增加话题维度（群会话从"一 chat 一会话"变为"一 chat 一话题一会话"）；
- 桌面端的会话映射、`/new`、工作区绑定、状态文件迁移同步调整。

这是本 spec 里唯一**架构级**的选择，其余能力都不依赖它。建议：**先做 G1–G5 + G10（不依赖话题维度），
再单独评估 D1**。若用户要一次性全对齐，则 D1 先行，且需要状态文件版本迁移。

**D2 排队可见的形态**（G1）。平台能力不同（微信无消息编辑、钉钉/企微/飞书各有差异），
可选：一次性文本提示 / 表情回应 / 排队卡片。建议按平台能力分档，至少保证"一次性提示"在所有通道可用。

## 产品规则

### R1 出站目标不变

所有新增出站（排队提示、引用回复、@ 回人、错误提示）一律经既有唯一目标函数
`resolveOutboundTarget(actor) = actor.chatId ?? actor.providerUserId`。
"降级"只允许换帧或改走主动推送，**不允许换收件人**（`bot-outbound-target.md` 规则 4）。

### R2 状态写入走既有唯一入口

新增的排队/历史/节流/去重状态一律经 `BotsRepo.mutateState(mutator)`（`bot-state-ownership.md`），
禁止新增第二份状态缓存或第二条写入路径。内存态（配额、去重表）若不需要跨重启，需在 spec 的
状态所有者一节显式声明为"进程内、可丢"。

### R3 群说话权只由既有开关决定

「私聊方式」+「群聊激活模式」是唯一的准入开关（`im-bot-onboarding.md` R2 的不对称保持）。
新增的 @ 解析、管理员关注等能力**不得**引入第二套授权模型。

### R4 平台能力分档，不造假界面

每项能力都要声明"该平台不支持时怎么办"。不支持就不做该交互，不做占位按钮、不做假成功。

### R5 clean-room 交付纪律

每个 PR 自检：新增代码的输入来源都在本 spec「允许的输入」清单内；diff 中没有上游实现内容的引用。

## 验收场景

1. **G1**：群内连发 3 条触发消息 → 第 2、3 条有可见的排队告知；补跑完成后顺序正确、无重复。
2. **G2**：单群 1 秒内产生 10 条出站 → 实际发送被节流到设定间隔，无平台风控错误。
3. **G3**：平台支持引用的通道，回复挂在触发消息下；不支持的通道走降级且**收件人不变**（回归 `bot-outbound-target.test.ts`）。
4. **G4**：群内多个不同昵称成员发言 → 历史与提示词中出现真实昵称；平台不返回昵称时仍显示兜底文案。
5. **G5**：模型要求 @ 某人 → 平台语法正确；解析不出唯一目标时退化为纯文本，不 @ 错人。
6. **G10**：两个机器人同在群里且互相可见 → 不会无限互答；同样两条消息不会二次触发。
7. **D1 若采用**：同一群两个话题并发提问 → 落在两条不同的桌面会话，互不串线；状态文件迁移幂等。
8. **回归**：`pnpm --filter @mode/services test`、`pnpm typecheck`、`pnpm lint`、
   `pnpm architecture:check --changed` 全绿；`node scripts/check-language-policy.mjs` 通过。

## 分阶段（建议）

## 风险

- **clean-room 边界**：本能力集在上游有成熟实现，最大风险是写成"换皮的同一套设计"。
  交付前需按政策做雷同自查；同名同形会直接被 M4 门禁判为重合。
- **D1 的迁移面**：会话键升维会牵动桌面会话映射与工作区绑定，迁移写错会丢对话上下文。
- **平台能力差异**：G1/G3/G5 在微信（无消息编辑、无 @ 语义）上会退化成最弱形态，
  需明确接受"微信体验仍弱于企微/飞书"。
